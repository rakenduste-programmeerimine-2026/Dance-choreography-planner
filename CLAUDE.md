## Choreography rules
These are the hard part. Follow them exactly.

Data
- Two tables only:
  - `choreographies`: `id`, `owner_id` (references `auth.users`), `title`, `stage_width_m` (default 10), `stage_depth_m` (default 8), `dancers` (jsonb array of `{ id, label, gender }`), `created_at`, `updated_at`.
  - `scenes`: `id`, `choreography_id` (cascade delete), `sort_order`, `name`, `transition_seconds` (default 4), `positions` (jsonb object keyed by dancer id: `{ x, y, waypoints: [{ x, y }] }`), `created_at`, `updated_at`. `(choreography_id, sort_order)` is unique and deferrable so reordering works in one transaction.
- Dancer `id` is a UUID from `crypto.randomUUID()`. `gender` is `mees` or `naine`. At most 30 dancers per choreography and 20 waypoints per path.
- Dancer `label` is 1–3 characters and unique within a choreography, ignoring case. A new dancer gets the next unused number as label and gender `naine`.
- Choreography `title` is required, trimmed, 1–100 characters, with no default. Scene `name` is trimmed, 1–60 characters, default "Stseen N" where N is the scene count plus one.
- Database CHECK constraints cover the scalar columns and the JSON top level: `stage_width_m` and `stage_depth_m` between 1 and 50, `transition_seconds` between 0.5 and 60, title and name lengths, `jsonb_typeof(dancers) = 'array'` with `jsonb_array_length(dancers) <= 30`, `jsonb_typeof(positions) = 'object'`. Everything inside the JSON (ids, label, gender, coordinates between 0 and 1, waypoint count) is validated by server type guards before every write.
- RLS: a user can read, insert, update and delete only choreographies where `owner_id = auth.uid()`, and only scenes of those choreographies. `anon` has no access.
- Any write that touches more than one row (creating a choreography with its first scene, reordering scenes, deleting a scene, adding or deleting a dancer across all scenes) goes through one `SECURITY INVOKER` Postgres function with `set search_path = ''`, so it is atomic and RLS still applies. Execute is revoked from `public` and `anon`.

Stage and scenes
- The stage is a rectangle seen from above, with the audience along the bottom edge (labeled "Publik") and meter labels on the edges. Background `slate-50`.
- The grid has lines every 1 m in `slate-300`. It is on by default in the editor and off by default in playback. The toggle is not saved.
- Stage width and depth are set when creating or renaming a choreography. Changing them stretches the positions, with the note "Mõõtude muutmine venitab paigutust".
- Coordinates are fractions of the stage, 0 to 1. `x` runs from stage left to stage right as seen from the audience. `y` runs from the back (0, top of the screen) to the front (1, bottom of the screen). Meters are used only for the grid and labels.
- A dancer is a dot with a short white label with a thin dark outline. `mees` is `blue-600` and `naine` is `pink-500`, defined once as theme colors. A selected dot or waypoint gets a dark ring, never a different fill.
- Every dancer is on stage in every scene. Adding a dancer adds them to every scene at the first slot of a fixed 6×5 grid that no dancer occupies in the shown scene, at that same spot in every scene. Deleting a dancer removes them from every scene.
- A choreography always has at least one scene: creating it also creates "Stseen 1", and the last remaining scene cannot be deleted.
- New scenes are added only at the end. A new scene starts as a copy of the last scene's positions with no waypoints.
- Whenever a scene's previous scene changes (reorder, delete), its waypoints are cleared, and the first scene's waypoints are always cleared. This happens inside the same database function. Moving a dancer keeps the existing waypoints.
- Deleting a choreography, dancer or scene asks first with `confirm()` and Estonian text naming the item, for example "Kustutan tantsija 3 kõigist stseenidest?". Removing a waypoint does not ask.
- Save after each completed edit (pointer up, rename confirmed), and show the save state: "Salvestatud", "Salvestan…" or "Salvestamine ebaõnnestus" with a "Proovi uuesti" button that resends the latest state. No automatic retry. Last write wins. There is no multi-user editing.

Paths and playback
- `waypoints` in scene N describe the path from the dancer's position in scene N−1 to their position in scene N. The first scene has no waypoints, and its `transition_seconds` is ignored.
- Before building a path, drop any point within 1e-9 of the point before it (equal waypoints, or a waypoint on an endpoint).
- One point left (the dancer does not move): the dancer stays put for the whole transition. Two points: a straight line. More points: a centripetal Catmull-Rom curve (alpha 0.5) through all points, which does not overshoot or loop. End tangents come from phantom points mirrored across each endpoint: `2·P0 − P1` at the start and `2·Pn − Pn−1` at the end.
- During playback a dancer moves at constant speed along the path, parameterized by arc length. Every dancer leaves at the start of the transition and arrives exactly when `transition_seconds` ends.
- Numeric tolerances for tests: endpoints within 1e-9; at time fraction t, the distance travelled along the curve is within 1e-3 (stage fraction) of t × total path length.
- Waypoint editing: tap or click a path to insert a waypoint at that spot in path order, drag to move it, tap to select and press "Kustuta punkt" or Delete to remove it. No double-click actions.
- Transition duration: a number input in seconds, step 0.5, range 0.5–60, default 4, shown only for scenes after the first. Saves on blur or Enter; out-of-range values show an Estonian error and are not saved.
- Playback runs at `/choreographies/[id]/play` and shows dots only: no paths and no editing handles. It has play/pause (resume continues from the same moment) and a choice of the scene to start from. No scrubber, no music sync.
- Timeline from start scene K: hold 1 s at scene K, play the transition to K+1, hold 1 s, and so on, stopping on the last scene. The 1 s hold is a constant in the pure timing module, not stored and not editable.

## Features (only these three)
1. Create, rename and delete choreographies. Add, rename, set gender for and delete dancers. Add, rename, reorder and delete scenes, and drag dancers to their places on the stage in each scene.
2. For each scene after the first, show every dancer's path from the previous scene and let the user add, drag and remove waypoints, and set the transition duration.
3. Play the whole choreography as an animation: scenes follow one another and dots move along their paths.

## Tests
Keep tests few and aimed at real risk.
- pgTAP (`supabase test db`): one user cannot read, change or delete another user's choreographies or scenes; `anon` sees nothing; the CHECK constraints reject bad values; reordering scenes keeps `sort_order` unique and clears waypoints of scenes whose previous scene changed; the last scene cannot be deleted; adding and deleting a dancer changes every scene or none.
- Vitest: the path rules above, including the stay-put and duplicate-point cases, the tolerances, and the JSON type guards rejecting malformed input.
- Playwright: a user creates a choreography, adds four dancers (two `mees`, two `naine`), places them, adds a second scene, moves dancers, adds a waypoint, sets a duration, reloads to check it saved, then plays the dance and the dots end at the second scene's positions.
- Playwright signs in a seeded local test user with email and password through the local Supabase API and sets the session cookies. Enabling the email provider in `supabase/config.toml` for this, for local use only, is pre-approved. The app gets no password sign-in UI, and the hosted project keeps Google only.
